# Adversarial review — inba.dev architecture spine

Verdict: **changes required**. The spine fixes the major deployment-mode ambiguity, but five material seams still allow independently built units to obey every AD while producing incompatible runtime or release decisions. Two are high-risk release-integrity gaps.

## Method

I treated each AD as a contract and attempted to build two independent implementations that satisfy its literal wording. A finding is included only where both implementations can remain compliant while disagreeing about shared data, state, fallback, evidence, promotion, or authority in a way that can change the shipped result or gate verdict.

## Findings

### High — Gate evidence is not cryptographically bound to the candidate static export

**Compliant divergence.** Builder A records the Git implementation revision and runs G4 against `out/` produced before a last uncommitted CSS change. Builder B rebuilds `out/` after that change. Both can record the same implementation revision, fixture revision, browser state, and artifact path and can claim that the “exact candidate artifact” passed, because AD-9 through AD-12 do not require an export digest, clean-tree state, or a digest carried by every evidence row. Cloudflare can then receive an export different from the one whose screenshots and budgets passed.

This is not closed by the evidence matrix’s `implementation revision` field: a revision does not identify generated bytes, local changes, environment-dependent output, or a later rebuild at the same revision.

**Required tightening.** Add a release-artifact identity AD, or extend AD-9/AD-11, requiring one immutable candidate ID derived from at least the static-export tree digest, source revision plus dirty-state assertion, lockfile digest, build command/config digest, and relevant toolchain versions. Every G1–G4 evidence row and the deployment record must reference that candidate ID. Any rebuild or mutation creates a new candidate and invalidates evidence tied to the old digest. Deployment must publish the already-verified artifact, not rebuild it.

### High — Baseline promotion is authorized but not defined as one atomic, auditable state transition

**Compliant divergence.** Promoter A copies a candidate PNG into `baselines/` and later updates `baseline-manifest.json`; promoter B updates the manifest and evidence matrix first, then copies the image. Both obey immutable baselines, versioned identities, specialist review, and orchestrator-only promotion. A failure or concurrent promotion between steps leaves a mixed state: a manifest pointing at missing/new bytes, an evidence row claiming a baseline that is not the file on disk, or two different images under the same `VA-<row>/<viewport>-<checkpoint>` identity.

The identity convention is also under-specified. `<viewport>` does not uniquely encode required width and height, DPR, browser, fixture revision, crop, or fallback condition. The capture matrix permits classes such as `>=1199px` and `901–1099px`, so two builders can choose different concrete viewports while emitting the same logical identity.

**Required tightening.** Add a baseline-registry/promotion AD that defines a canonical manifest schema and uniqueness key; content hashes for baseline bytes; exact viewport width/height, DPR, browser, checkpoint/fallback state, fixture revision, and crop/mask policy; and an atomic promotion operation that commits candidate bytes, manifest entry, review verdict, evidence row, and supersession link together. Promotion must use compare-and-swap or an equivalent single-writer check against the reviewed candidate hash. Promoted bytes are append-only; replacements receive a new version and explicit supersession rather than overwriting the prior identity.

### Medium — The “shared” eligibility policy has no single state owner or committed snapshot protocol

**Compliant divergence.** `PinnedSequenceController` and `WebGLSubstrate` can each import the same pure eligibility function yet sample media queries, viewport height, font readiness, content fit, and probe status at different instants. Pinning can commit `true` from one snapshot while WebGL commits `false` from another. A resize or font event can then make one island tear down before the other, even though both re-evaluate on every lifecycle trigger. Both implementations comply with AD-4 and the convention that state is local to islands.

The conflict is structural: AD-4 requires one shared eligibility policy and committed lifecycle triggers, while the state convention forbids a coordinating page client but does not identify an owner for the common environment snapshot, trigger ordering, cancellation of stale probes, or subscriber teardown ordering.

**Required tightening.** Amend AD-4 with a framework-neutral ownership contract: one environment snapshot type, one monotonic generation/epoch, one trigger coalescing rule, and one shared read-only eligibility service/store outside component state. All islands evaluate and commit against the same generation; stale async WebGL probes cannot commit. Specify teardown ordering and the settled-state postcondition. Keeping the page shell server-rendered does not preclude a small shared external store.

### Medium — Failure and performance fallbacks lack a deterministic state machine

**Compliant divergence.** One WebGL implementation measures the first 30 frames, includes shader compilation, and permanently disables at median 54fps. Another waits for warm-up, measures 120 foreground frames, and stays enabled. Both follow “below median 55fps.” Likewise, “repeated frames over 25ms,” “repeated failure,” background-tab recovery, context restoration, and “for the session” have no sampling window, count, cooldown, persistence scope, or retry policy. Asset components can also interpret a declared fallback as permanent after one failed derivative or recover when a later `srcset` candidate succeeds; both preserve geometry and content under AD-6.

These choices change whether eligible users receive the enhancement and whether VA-14/VA-16 pass, so they are architecture behavior rather than deferred shader detail.

**Required tightening.** Add a fallback-state AD or extend AD-4/AD-6 with named states and transitions. For WebGL, define probe, warm-up, sample window, foreground-only timing, slow-frame count, context-loss/retry limits, session persistence key/scope, and terminal static state. For media, define which failure is derivative-local versus asset-terminal, whether retry is allowed after source/environment change, and the semantic/DOM form of informative versus decorative fallback. Tie VA-14 and VA-16 checkpoints to these states.

### Medium — Specialist authority does not enforce separation of duties or exception lifecycle

**Compliant divergence.** The same agent can act as primary implementation owner and strong orchestrator: AD-12 says only the implementation owner edits code and only the orchestrator promotes, but never says those principals must differ. A specialist can submit a material failure; the orchestrator can “resolve reviewer conflicts” or approve a scoped exception and promote anyway. Another orchestrator can treat the same finding as blocking. Both obey AD-12 because the distinction between review recommendation, gate approval, conflict resolution, and exception override is not formalized.

Expiry is equally ambiguous. An exception has an owner/expiry in the evidence matrix, but no AD says an expired exception automatically invalidates the gate, which gates may admit exceptions, whether a material G4 finding is exceptionable, or who may renew it.

**Required tightening.** Extend AD-12 with a role/decision matrix and separation constraints: implementation author cannot be the promoter for their candidate; each required specialist owns pass/fail for its assigned evidence domain; the orchestrator verifies completeness and advances only when all blocking domain verdicts pass. Define conflict escalation without converting a failure to pass. Define exceptionable severities/gates, required rationale and compensating evidence, expiry behavior, renewal authority, and automatic gate invalidation on expiry. Record immutable actor identities and timestamps, not only role labels.

## Secondary observations

- AD-2 establishes module ownership but not the typed export/schema contract. Independent builders can choose arrays versus keyed records, incompatible artifact-key enums, or different nullability while remaining compliant. A canonical exported type file or schema should bind consumers. This is a real integration risk but lower than the gate-integrity seams above because TypeScript will expose most mismatches when units are integrated.
- `content/assets.ts` “projects” both spec asset rules and the mock asset manifest without stating precedence or a source revision. Add explicit precedence and schema validation so two asset-pipeline builders cannot resolve a conflict differently.
- AD-9 correctly fixes v1 to Cloudflare Pages static export. It should also name the canonical publish directory/config and route/404/trailing-slash expectations, but that refinement becomes straightforward once the release-artifact identity is defined.

## Retest condition

Re-run this review after the spine defines: (1) immutable candidate-export identity, (2) atomic versioned baseline promotion, (3) one generation-based eligibility snapshot owner, (4) deterministic fallback state transitions, and (5) enforceable review/promotion/exception authority. The first two should block architecture acceptance; the remaining three should be resolved before parallel implementation begins.

## Final re-review — updated spine

Verdict: **changes still required, narrowed to two material holes and one registry refinement**. Exact-export binding, atomic promotion, revisioned eligibility ownership, stale-result rejection, and reviewer/implementer separation are now closed at architecture-spine altitude. Fallback terminality and exception expiry remain open.

### Closure check

| Prior attack | Re-review result | Basis |
| --- | --- | --- |
| Evidence can describe different bytes than deployment | **Closed** | AD-9 makes the generated `out/` digest the verification and deployment identity, requires every release-evidence item to name it, and requires Cloudflare to receive identical bytes. The build-reproducibility convention pins Node/npm, lockfile installation, and build command. |
| Baseline files, manifest, review, and supersession can be promoted separately | **Closed** | AD-10 requires one atomic commit of baseline files, manifest metadata, source revisions, reviewer decision, and superseded IDs, and declares partial promotion invalid. | Islands can evaluate different environment snapshots or commit stale probes | **Closed** | AD-4 assigns one `EnhancementEligibility` owner, revisioned immutable snapshots, and explicit rejection of async results from older revisions. | Reviewer can be the builder or promoter can have implemented the slice | **Closed** | AD-12 makes specialist reviewers distinct from the implementation owner and requires the promoting orchestrator not to have implemented the reviewed slice. |

### Remaining high — Exception expiry is metadata, not a gate transition

**Counterexample.** Orchestrator A considers an exception valid because it was approved when G3 passed, even though its expiry precedes G4. Orchestrator B rejects the same candidate at G4 because the exception is expired. Both comply: AD-12 requires recording expiry but never says an exception must be unexpired at promotion time, automatically invalidates affected rows on expiry, or blocks deployment after expiry.

**Required tightening.** State that every gate evaluation checks exception validity against a defined clock; an expired exception immediately invalidates its affected evidence rows and prevents advancement or deployment until evidence passes or a separately audited renewal is approved. Define who may renew, require renewal before expiry, and preserve the old exception plus renewal as append-only records. Also state whether G4 admits any exception beyond the three explicitly non-waivable domains.

### Remaining medium — Runtime failure can oscillate instead of honoring session-terminal fallback

**Counterexample.** WebGL falls below median 55fps. Implementation A marks the fallback terminal for the browser session, matching `visual-acceptance.md`. Implementation B tears down and re-enables on the next eligibility snapshot because AD-4 explicitly allows a later snapshot to re-enable after “runtime failure.” Both obey the architecture text, but one can repeatedly import, fail, and remount the expensive scene.

The trigger predicates also remain non-equivalent: builders may choose different warm-up periods, sample windows, definitions of “repeated” frames over 25ms, context-loss counts, and background-tab treatment while all claiming the same VA-14 behavior.

**Required tightening.** Split runtime failures into recoverable and terminal classes. Preference/viewport changes may recover on a later eligible revision; low-frame-rate and repeated-context-loss failures enter a session-terminal static state that eligibility snapshots cannot clear. Bind the measurement protocol: warm-up, foreground-only sample window, slow-frame count, context-loss limit, and session scope. VA-14 evidence should name the reached state and transition cause.

### Remaining medium — Baseline transaction is atomic, but its logical identity can still collide

**Counterexample.** Two promoters capture `VA-05/desktop-settled` at different concrete desktop widths, heights, DPRs, or browsers. The evidence rows preserve those dimensions, yet the baseline convention gives both the same logical ID because `<viewport>` may be a class label. Atomic promotion prevents partial writes but does not prevent two incompatible baselines from competing for one identity.

**Required tightening.** Define the canonical baseline uniqueness key or require the manifest to version each exact tuple of acceptance row, width, height, DPR, browser profile, checkpoint/fallback state, fixture revision, crop/mask policy, and content digest. A replacement must use a new immutable ID and an explicit supersession edge.

### Consistency cleanup

The design paradigm and structural seed now define three client islands, while the State and cross-cutting convention still says “five bounded client islands.” Replace the count with the named current islands or “bounded client islands” so it cannot authorize obsolete `PortraitRegistration` or `SectionDisclosure` units.

### Final gate recommendation

Do not accept the architecture as final until exception expiry has blocking semantics and WebGL terminal failures cannot be re-enabled by a routine eligibility revision. Baseline-key uniqueness should be fixed in the same edit because parallel fixture generation will otherwise recreate the collision AD-10 is meant to prevent.

## Final critical/high verification

Verdict: **pass — no remaining critical or high divergence holes found**.

The final attack confirms that the release artifact is bound by the `out/` digest through evidence and deployment; baseline promotion is atomic and baseline identity now includes the concrete capture tuple; eligibility has one revisioned snapshot owner with stale-result rejection; WebGL initialization and repeated-context-loss failures are session-terminal while VA-14 supplies the low-frame-rate session fallback; implementation, specialist review, and promotion are separated; and expired exceptions automatically invalidate affected rows and block promotion or deployment.

Residual choices such as the exact low-frame-rate sample window, exception-renewal procedure, typed content export shape, and asset-manifest precedence are implementation or medium-level contract refinements. None lets two AD-compliant builders bypass a release gate, deploy different bytes under the same evidence, self-promote, or keep an expired exception effective.
